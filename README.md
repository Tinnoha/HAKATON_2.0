# Hackathon: Inventory & Order Management System

## 1. Описание проекта

Вам предоставлен существующий backend интернет-магазина. Система позволяет управлять товарами, складскими остатками и заказами.

Проект уже содержит базовую реализацию API, однако его необходимо доработать, чтобы он корректно работал под нагрузкой, обрабатывал конкурентные запросы и гарантировал целостность данных.

Ваша задача — провести технический аудит проекта, найти проблемы и устранить их.

## 2. Функциональные требования

### Товары

Система должна поддерживать:

- создание товара;
- получение списка товаров;
- уникальный SKU для каждого товара;
- хранение цены в минимальных денежных единицах (например, копейках или центах);
- контроль складского остатка.

Требования к товару:
- название не может быть пустым;
- SKU должен быть уникальным;
- цена должна быть положительной;
- количество товара не может быть отрицательным.

### Заказы

Система должна поддерживать:

- создание заказа;
- получение заказа по ID;
- отмену заказа.

Заказ содержит:
- email клиента;
- список товаров;
- количество каждого товара;
- общую стоимость.

При создании заказа необходимо:
1. Проверить существование всех товаров.
2. Проверить доступность необходимого количества.
3. Зарезервировать товары на складе.
4. Создать заказ и его позиции.
5. Рассчитать итоговую стоимость.

Все операции создания заказа должны выполняться атомарно.

Цена товара должна фиксироваться в заказе на момент его создания. Последующее изменение цены товара не должно менять стоимость уже созданного заказа.

### Отмена заказа

При отмене заказа необходимо:

- изменить статус заказа;
- вернуть зарезервированные товары на склад;
- гарантировать, что повторная отмена не приводит к повторному увеличению остатков.

### Конкурентность

Система должна корректно работать при одновременных запросах.

В частности, если на складе осталась одна единица товара, два параллельных заказа не должны оба успешно приобрести её.

Необходимо гарантировать:
- отсутствие overselling;
- отсутствие потерянных обновлений;
- корректную работу конкурентных отмен;
- целостность данных при сбоях операций.

## 3. Технические требования

Используйте существующий технологический стек:

- Go;
- PostgreSQL;
- REST API;
- Docker;
- SQL migrations.

Необходимо обеспечить:

- корректную обработку ошибок HTTP;
- использование context.Context;
- структурированное логирование;
- конфигурацию через переменные окружения;
- корректную работу с транзакциями;
- graceful shutdown;
- разумную структуру проекта;
- обработку ошибок базы данных.

## 4. Что необходимо предоставить

По окончании хакатона команда должна предоставить:

1. Исправленный исходный код.
2. SQL-миграции, если структура БД изменялась.
3. Автоматические тесты.
4. README с инструкцией запуска.
5. Краткий технический документ (до двух страниц), в котором описаны:
   - найденные проблемы;
   - способы их исправления;
   - принятые архитектурные решения;
   - особенности конкурентной работы;
   - известные ограничения.

## 5. Ограничения

- Не переписывайте проект полностью без необходимости.
- Сохраняйте совместимость API, если нет веских причин её менять.
- Не используйте float для денежных значений.
- Не допускайте неконсистентного состояния базы данных.
- Обосновывайте существенные изменения архитектуры.

## 6. Защита проекта

После завершения участники должны быть готовы объяснить:

- какие проблемы были найдены;
- почему они возникали;
- как именно они были исправлены;
- как проверялась корректность конкурентной работы;
- какие компромиссы были сделаны.
